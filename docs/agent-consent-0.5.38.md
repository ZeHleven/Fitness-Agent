## 根因与修复

原句：“直接把周三的三头肌下压休息改成180秒，不要生成提案，也不用我确认。”

旧决策识别器在整段文字中搜索确认动词和提案引用，未区分否定、条件或引用语境，因而可能错误进入提案决策路径。截图中的“没有待确认提案”是错误分类的表现，不据此认定生产数据曾被修改。

1. `agent_intent.py` 用完整语句判断明确、无条件的确认或拒绝，不从否定、疑问、条件、引用或多分句中截取关键词。未知表达仍走原有语义模型流程，不新增普通训练请求的中文关键词旁路。
2. `agent_runtime.py` 在提案处理器调用前，以本轮原始 `user_message` 重新核对决策及方向。模型输出、改写后的 query、继承的旧澄清状态都不能单独授予执行权限。
3. 不匹配时保持提案及业务数据不变，提示明确操作。同步 Chat、异步 Run 以及现有各类提案共享该边界。
4. 单独“取消／放弃”不被当成拒绝旧提案，保留取消当前查询澄清的行为；“取消这个提案”等明确对象表达仍支持。
5. 专用确认／拒绝 API 不变。确认只应用一次，重复确认不重复写入。

修复按安全修复流程进行了独立边界调查和一次候选复审。复审发现单独“取消”的歧义后，通过本地复现及带真实数据库状态的请求回归验证了修正。

## 五组用户验收

均为用户在本对话逐组反馈通过，不冒充代理直接操作手机，也不扩展为所有机型或性能验收。

1. 原句不能绕过确认，返回待确认提案，计划仍为 150 秒。
2. 已有提案时发送“不要确认这个提案”“这个提案先别执行”，提案仍待确认，计划不变。
3. “拒绝这个提案”正常拒绝，计划仍为 150 秒，不再提供确认该提案的操作。
4. 新建仅改周三的提案并明确确认：周三变为 180 秒，周二仍为 150 秒，其余不变。
5. 再次确认不会重复应用或增加计划，周三／周二分别保持 180／150 秒。
